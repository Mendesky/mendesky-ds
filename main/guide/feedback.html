載入與回饋 ​

這篇處理兩件事。第一，資料還在載入時，畫面要顯示什麼。第二，使用者按下建立、修改、刪除之後，要給什麼回饋。

做會讀寫後端的區塊、或接上送出按鈕之前，先讀這篇。

先判斷 ​

載入中 ​

「水合」指打開畫面時，向後端取回既有資料、填進欄位的過程。skeleton 是用形狀塊暗示內容位置的佔位畫面。

為什麼要在意：如果使用者在資料回來之前就操作欄位，空值會被寫回後端，蓋掉真正的資料。

區塊的狀況做法
打開時向 API 取預填值，而且欄位 blur 或選取時會寫回後端載入期間用 skeleton 蓋住整個區塊，不能操作。資料回來才換成真的表單
只讀 API、不寫回後端不必用 skeleton
從父層的快照還原，不打 API直接顯示，不用 skeleton
API 失敗、離線、逾時收起 skeleton，顯示空白表單。不跳 toast 或 Dialog
整頁資料載入前用 Page Skeleton 佔位，避免版面跳動

送出之後 ​

「mutation」指會改變後端資料的操作：建立、修改、刪除。回饋策略分兩種：

  • pessimistic：等後端回應成功，才更新畫面。
  • optimistic：先更新畫面，後端失敗再還原。
操作策略畫面怎麼反應
Wizard、Dialog、多欄位表單按確認pessimistic按鈕轉為 loading。成功才關閉，並顯示成功 toast。失敗保留表單內容，顯示錯誤 toast
單一開關、下拉選單、就地編輯optimistic畫面立刻變。失敗還原成舊值，顯示錯誤 toast。成功通常不跳 toast
沒有存檔按鈕、逐欄自動存檔的介面optimistic例外：每存一欄就跳一顆成功 toast，依序堆疊
開關選到某個值後，要開 Wizard 補資料pessimistic選的當下不打 API。Wizard 確認才送出；取消就把開關還原
耗時操作，處理中要擋住整個畫面—用 Process Modal 的 type="running"，處理中不能關閉

情境與範例 ​

載入中：skeleton ​

Page Skeleton 是整頁載入用的佔位元件，沒有任何屬性。區塊層級的 skeleton 怎麼跟載入狀態同步，看下方規則「API 水合 Skeleton」。重點是 API 失敗時也要收起 skeleton，否則畫面會永遠卡在載入中。

送出中：按鈕 loading ​

html
<app-button
  variant="filled"
  color="primary"
  size="M"
  text="確認建立"
  [loading]="submitting()"
  (btnClick)="confirm()"
></app-button>
vue
<DsButton
  variant="filled"
  color="primary"
  size="M"
  text="確認建立"
  :loading="submitting"
  @btn-click="confirm()"
></DsButton>
  • loading 為 true 時，轉圈取代 icon，底色不變，點擊無效，所以不會重複送出。
  • 要在 loading 時換文字，用 loadingText。
  • Dialog 的確認按鈕也有 loading。
  • 送出中，Wizard 的 X、ESC、背景都不能關。X 鈕傳 disabled；ESC、背景與自訂的「取消」按鈕，處理函式在送出中直接 return。

操作結果：toast ​

按下面的按鈕，看成功、錯誤、含復原三種 toast。

ts
private readonly toast = inject(ToastService);

this.toast.show({ type: 'success', message: '已儲存' });
text
尚無 Vue 版：#toast-container、#process-toast
  • 整個 app 只在 app root 掛一次 Toast Container 全域 Toast 容器。要顯示 toast 就呼叫 toast 服務的 show()。不要自建 toast 堆疊，否則兩套堆疊會互相遮蓋。
  • 停留時間由類型決定，不用自己傳：成功與載入中 3 秒；錯誤與帶 action 的 5 秒。
  • 只有帶 action 的 toast 可以點。其他 toast 不接收點擊，避免擋住底下的按鈕。
  • 訊息最多顯示兩行，超過的部分會直接被截掉，不會報錯。
  • 同一件事的「進行中 → 完成」用一顆 toast 原地轉換。不同的事各自一顆，依序堆疊。
ts
// 同一件事的兩個階段：先顯示進行中，完成後原地更新
const id = this.toast.show({ type: 'loading', message: '文件產生中', persist: true });
// …完成後
this.toast.update(id, { type: 'success', message: '已開始下載' });
text
尚無 Vue 版：#toast-container、#process-toast

<app-process-modal

  [isOpen]="isProcessing()"
  (dismissed)="onDone()"

尚無 Vue 版：#process-modal
  • type="running"：白底小卡加轉圈，蓋住整個畫面，處理中不能關閉。
  • type="congratulation"：綠底慶祝卡，點背景會觸發 dismissed 事件。

規則 ​

API 水合 Skeleton loading.api-hydration-skeleton

原則：Section 同時具備「開啟瞬間打 GET API 取得預填值」與「欄位 blur/select 觸發寫入 API」時，GET 未回 + 使用者先操作 = 寫入會把 null/空字串送回後端覆蓋真值。用「載入中」旗標（loading）驅動 skeleton 遮罩整段 section 在 race window 內不可互動，API 回來才切換到真實表單。禁止用反向 hydrated 旗標（雙重否定、可讀性差）。

什麼時候用：Section 內同時有「讀取 API 預填」與「寫入 API（blur/select/debounce 觸發）」；或任何狀態值在 API 回來前被使用者互動讀走會造成資料損失的情境。

情境說明規則
apiHydratedReadWriteSection 同時讀 API（GET 回來填入欄位狀態）且寫 API（blur/select 觸發 edit）
為什麼：四個同步點（初始 true / loadFromApi 設 true / apply 設 false / catch 設 false）缺一就會造成卡死或 race；只在單一處判斷（一個條件分支）避免散落的衍生狀態洩漏中間態
  • 載入中旗標初始為 true；loadFromApi 第一行設為 true
  • 對應的套用函式（apply*）尾端、把完整狀態 emit 給父層之後設為 false
  • loadFromApi 的 .catch 必設為 false，否則 API 失敗 → skeleton 永卡
  • 模板只用一個條件分支切換：載入中顯示 skeleton，否則顯示真實表單，兩者不可並存
  • 父層傳入 initialState 時（含第一次傳入與之後每次變動）、走「從 snapshot 還原」分支時設為 false（snapshot 已含值、不必等 GET）
  • 父層傳入資料時（含第一次傳入與之後每次變動）的 reset 分支用 loadFromApiFiring 判斷：若本輪會觸發 loadFromApi，設為 false 交給 loadFromApi；否則主動設為 false
  • 清單型 section 同理：GET 回來整份覆寫清單，會把使用者剛上傳或新增的項目沖掉，同樣要用 skeleton 遮住 race window
apiHydratedReadOnlySection 只讀 API、沒有寫入 API（例如純展示或只 emit 給父層）
為什麼：沒有寫入 API 就不會有「被覆蓋」的資料損失；裝 skeleton 只是 UX 偏好，不是正確性需求
  • 不必裝 skeleton；沒有 race window 可遮
  • 若 UX 希望有 loading 視覺 → 再考慮 skeleton，但不屬於此 pattern 範疇
localSnapshotOnlySection 從 parent 的 initialState 快照還原，整段不打 API
為什麼：Snapshot 是 UI 草稿，不是後端真值；但 UI 可立即顯示，skeleton 沒有存在理由
  • 偵測到父層傳入的 initialState 存在 → 直接從 snapshot 寫回欄位狀態，並把載入中旗標設為 false
  • 若 snapshot 不完整仍需 GET 補 → 走 apiHydratedReadWrite，snapshot 分支也要設為 false（因為 UI 可立即顯示，GET 只補背景資料）
failSilentAPI 失敗 / 離線 / timeout
為什麼：永久 skeleton 是比錯誤訊息更糟的 UX；讓使用者能填表單 > 顯示錯誤
  • .catch callback 內第一件事：把載入中旗標設為 false
  • 接著 console.error 記錄失敗原因
  • UI 顯示空白表單（使用者可手動輸入、blur 會觸發重試）
  • 不彈 toast / dialog（避免打斷；parent 層若需 retry UI 再另外處理）
raceRetryReadRead API 對應 CQRS aggregate，剛 POST 建立後 read model 尚未就緒（race window < 1s），會回 503
為什麼：對齊後端 API 規格「呼叫端應有 retry 策略」的約定；指數退避讓 projection 提前就緒時更快結束，總上限約 1.4s（200×2^(n-1) 退避三次加總）對後端 race window < 1s 規格留約 40% margin。實際值以共用 const（RACE_RETRY）為準，避免每個 service 重抄 delay 數字
  • 讀取用的 service 層對 GET 套用重試設定 RACE_RETRY；RACE_RETRY 是使用端共用的 retry 設定常數，由使用端自行提供、不在 DS 套件內（它綁定的是後端的 retry 約定與 503 語意，屬於 app 與後端之間的協定而非 UI 行為）
  • 請求同時帶「抑制錯誤 UI」旗標（抑制 retry 期間的 503 dialog）＋「抑制 404 UI」旗標（保留 404 → null fallback 行為）
  • 順序：先重試、後做錯誤處理（404 不 retry、其他 status 跑完 retry 才進錯誤處理）
  • retry 用盡仍 503 → 拋給呼叫端 → 元件 catch 走 failSilent（console.error + skeleton 收起 + 不彈 dialog）
  • 不適用 PATCH / POST — 只適用 GET read model；寫入端的並行撞擊要用依序送出（serialize）而非 retry

不要這樣做

  • 用反向旗標 hydrated（初始 false）→ 雙重否定；模板判斷「還沒 hydrated」易讀性差，父層資料變動的分支容易忘記翻轉
  • 忘記在 catch 內設為 false → 網路一掉使用者看到永恆 skeleton，只能重整頁面
  • 載入中旗標被散落消費（多處衍生狀態 / 多個條件分支分散判斷）→ 中間態洩漏，skeleton 閃爍
  • Skeleton 畫太細（1:1 對應每個欄位）→ 表單類型切換時 skeleton 欄位數不對，比真實表單還難維護
  • apply* 設為 false 的位置放在「emit 完整狀態給父層」之前 → 先關 skeleton 再 emit，中間一瞬間畫面切到真實表單但欄位狀態還沒寫完，使用者看到空表單
  • 父層傳入資料時（含第一次傳入與之後每次變動）的 reset 分支無條件設為 false → 覆蓋後置的 loadFromApi 設 true，skeleton 根本不會亮

無障礙

  • 鍵盤：Skeleton DOM 內無 tabindex / focusable 元素 → Tab 自動跳過該 section；API 回來 skeleton 銷毀 → 焦點管理交給父層（wizard 有自己的 focus-first-field 邏輯）
  • ARIA：Skeleton 容器可選 aria-busy="true"（若整段 section 有 labelled 區塊），但本 pattern 不強制 —— 短於 500ms 的 hydration 不值得通知螢幕閱讀器；超過 1 秒的 hydration 才考慮 aria-live="polite"；GET API 普遍 < 500ms 時不必加
  • 動態：Shimmer 動畫使用全域 .sk-shimmer（linear-gradient + 1.4s loop）；prefers-reduced-motion 由全域 .sk-shimmer 處理，pattern 層不重複定義

Angular 做法

  • 載入中旗標用 signal：loadingSignal = signal(true)；loadFromApi 第一行 loadingSignal.set(true)。
  • apply* 尾端先把完整狀態 emit 給父層，再 loadingSignal.set(false)。
  • loadFromApi 的 .catch 第一件事是 loadingSignal.set(false)，否則 API 失敗 skeleton 永卡。
  • 模板寫法：@if (loadingSignal()) { <skeleton> } @else { <real form> }，不可並存。只用這一個 @if 讀 loadingSignal()，不要另外用多個 computed 或多個 @if 分散判斷。
  • 父層傳入資料的變動在 ngOnChanges 處理：initialState restore 分支（含 localSnapshotOnly：從 snapshot set 各欄位 signal）結尾 loadingSignal.set(false)。
  • ngOnChanges 的 reset 分支用 loadFromApiFiring 判斷：本輪會觸發 loadFromApi，就把 set(false) 交給 loadFromApi；否則主動 loadingSignal.set(false)。
  • 清單型 section：GET 回來對清單 signal 呼叫 set(...) 整份覆寫，會把使用者剛上傳或新增的項目沖掉，同樣要用 skeleton 遮住 race window。
  • 不要用反向旗標 hydrated = signal(false) 搭 @if (!hydrated())：雙重否定、易讀性差，ngOnChanges 分支容易忘記翻轉。
  • apply* 的 loadingSignal.set(false) 不可寫在 emit 之前：@if 會一瞬間切到 @else，但 signals 還沒寫完，使用者看到空表單。
  • ngOnChanges 的 reset 分支不可無條件 loadingSignal.set(false)：會覆蓋後置的 loadFromApi set(true)，skeleton 根本不會亮。
  • raceRetryRead（剛建立後讀 read model 的 503）：service 的 GET 走 RxJS pipe，retry(RACE_RETRY) 在前、catchError 在後（404 不 retry，其他 status 跑完 retry 才落到 catchError）。
  • raceRetryRead：「抑制錯誤 UI」與「抑制 404 UI」兩個旗標用 HttpContext 帶在同一個請求上。
  • raceRetryRead 不適用 PATCH / POST：寫入端的並行撞擊用 concatMap 依序送出（serialize），不用 retry。

Mutation API 反饋策略 mutation.feedback

原則：依「操作代價」決定策略：多欄位表單 / wizard confirm → pessimistic（await 後才更新 UI）；原子互動（單一 toggle / select）→ optimistic（UI 先動，失敗 rollback）。原子互動若連動後續 wizard，視同 wizard pessimistic 流程——原子階段不 fire API。

什麼時候用：任何 component 觸發後端 mutation 時；設計 wizard confirm handler / toggle change / inline edit 的 API 呼叫時機與失敗反饋策略時。

情境說明規則
pessimisticWizardWizard / dialog / 多欄位表單的確認按鈕觸發 mutation
為什麼：多欄位收集代表使用者有明確意圖；失敗後看不到表單 = 必須重填所有欄位（代價高）。pessimistic 把「狀態一致性」拉到 API 確認後，failure path 保留表單讓重試成本趨近於 0。
  • 按下「確認建立」→ button 進入 loading 狀態（Button 的 loading 屬性，自動阻擋重複 click）
  • await API call（不先更新前端 state）
  • 成功 → 關 wizard / dialog；插入新資料（含後端回傳的 id）；顯示 success toast（文案：「已新增」）
  • 失敗 → 保留 wizard / dialog 開啟；保留表單所有欄位值；顯示 error toast（文案：「建立失敗，請重試」）；button 退出 loading
  • 提交進行中：wizard 的 X / ESC / backdrop 全鎖（modal.dismissal.savingLocked）
  • 以 wizardSubmitting 狀態驅動 isSubmitting → button loading；cancel guard；父元件 try/await/finally 控制
optimisticAtomic單一 toggle / select / inline edit 觸發 mutation（無後續 wizard）
為什麼：單一欄位操作密集、低風險；pessimistic 每次都卡 spinner 阻礙流暢操作。UI 立即反映給使用者「你的操作被接受了」的感知，失敗時 rollback 並 toast 提示即可補救。
  • UI 立刻反映新值（不等 API）
  • 背景 fire-and-await API
  • 失敗 → rollback UI 回舊值；顯示 error toast
  • 成功 → 通常不需 toast（除非是高重建成本操作，例如某個開關要實際寫入後才算生效）
  • **例外：自動存檔介面（無存檔按鈕、逐欄 blur/選取即存後端）成功必發 per-field toast**——這類介面沒有「送出」動作，toast 是使用者唯一能知道「資料真的存進去了」的訊號。文案「<欄位名稱> 已儲存」。清空欄位也一律發 toast，否則使用者以為清空沒生效
  • 同上例外的兩個實作紀律：(1) toast 必貼在 API `await` 之後、同一個 `try` 內——多數 handler 的 early-return（`if (!id) return`）在 try 之外，放錯位置會對「根本沒打 API」的路徑發假回饋；(2) **一欄一顆、依序堆疊**（toast 服務的 `show()`），不得取代——「存了電話」與「存了地址」是兩件事。逐欄存檔 toast 的封裝（例如使用端自己包一層的存檔 toast 服務）由使用端實作，不在 DS 套件內
  • 逐欄存檔的 toast 不套用「取代不堆疊」：(a) `reversibleToast` 的「同一操作連續觸發 → 取代不堆疊」限定在**帶「復原」action 的可還原操作**，取代是為了不累積一排失效的復原鈕；(b) toast 服務 `update()` 的用途是**同一件事的「進行中→完成」原地轉場**（例如產生 PDF：生成中→已開始下載），那是一件事的兩個階段、不是兩件事
  • duration 由型別決定，呼叫端不自帶：success / loading → 3000ms、error → 5000ms、有 action → 5000ms（由元件統一決定，避免各呼叫點手打、漏帶就退回 3 秒）。實作於 toast 服務內部的同一個 resolveDuration 函式，`show()` 與 `update()` 共用——`update()` 會改 type（loading→error），只改一處會讓轉場後的 error 只停 3 秒
  • 文案長度：`.toast__msg` 有 `-webkit-line-clamp: 2`，過長**不報錯、直接靜默截斷**；硬截斷點約 29 全形寬（size S 桌機兩行）。插值的 runtime 長度必須有界——不定長清單（`join`）、名稱、檔名不得塞進 toast，改用「N 個／N 筆」計數，明細改 dialog 或頁面內呈現。各類型的字數上限（例如 success/loading 16 全形寬、error 24、有 action 18）與是否用腳本守門由使用端自訂、不在 DS 套件內——DS 交付的是「兩行截斷」這個視覺約束事實，上限幾字取決於各產品的語言與語境（中英文容忍度不同）。參考：Ant Design 有文案規範頁但只有定性建議、無字數上限、無工具；Bootstrap 完全不提文案；Atlassian 的 ESLint plugin 明文「並非內容或文案規範」——三個主流 DS 都不用工具管文案長度
  • 進行中可選：spinner 覆蓋原子元件（如 select）或維持 optimistic 無 spinner
pessimisticTriggersWizard原子互動（toggle / select）選到特定值後需要開 wizard 補資料
為什麼：若原子 change 同時 fire API + 開 wizard，wizard 收集到的補充欄位「後端先拿到 null 版本」→ 422；設計意圖是 wizard 確認後才算一次完整 mutation。分離兩條路徑才能保證資料完整性。
例：某張設定卡片的開關從 `no` 切到 `yes` 後要開 wizard 補資料：同一次 change 同時冒泡觸發「同步到後端」與「開 wizard」。修法：同步 handler 過濾這個 key；只有 wizard confirm 才呼叫建立 API。
  • 原子操作階段：不 fire 任何後端 API（哪怕 sig 已變更）
  • 開 wizard 收集缺少的欄位
  • Wizard confirm 才是唯一的 API fire 時機（視同 pessimisticWizard）
  • 使用者取消 wizard → 將原子元件值 rollback 到觸發前的狀態
  • 技術實作：若同一次互動同時冒泡「同步到後端」與「欄位設定變更」兩個事件，同步 handler 必須過濾會觸發 wizard 的那個 key（early return），由開 wizard 的 handler 獨立控制流程
savingLockedSurfaceWizard / dialog 的 loading 中斷保護（與 modal.dismissal.savingLocked 對齊）
為什麼：使用者在 API in-flight 時關掉 wizard 會導致「後端建立成功但前端不知道」的 ghost state；全鎖比允許部分互動更可預測。
  • wizardSubmitting = true 時：X 按鈕、ESC、backdrop 點擊全部 no-op（見 modal.dismissal.savingLocked）
  • 放進 wizard 自訂內容區的「取消」按鈕也需 guard：wizardSubmitting 為 true 時直接 return
  • 保護範圍：整個 try/await/finally 區間，不只是 API call 本身

不要這樣做

  • 原子 toggle 直接 fire 後端，但該 toggle 會觸發後續 wizard → 後端先拿到不完整資料（422）；正確：原子階段不 fire，wizard confirm 才是 mutation 時機
  • Wizard confirm 不 await API 直接關 wizard → 使用者以為完成，但 API 可能失敗，前後端狀態不一致
  • Optimistic update 有 fire API 卻沒寫 rollback → API 失敗後 UI 顯示不存在的狀態，無告知
  • 成功或失敗都不給 toast → 使用者無法確認「動作有沒有成功」，需回頁面驗證
  • API 失敗時清空 wizard 表單值 → 使用者必須重填所有欄位，重試成本高
  • Pessimistic wizard 但 wizardSubmitting guard 未覆蓋 X / ESC / backdrop → API in-flight 時可關掉 wizard，產生 ghost state
  • 用文字切換 button text 代替 loading 屬性 → 缺少 spinner 視覺、缺少自動 click 阻擋、語意不明確

無障礙

  • 鍵盤：按鈕 loading 中：aria-disabled="true"（仍可被 Tab 聚焦）+ aria-busy="true"；native disabled 改用 aria 方式；Success / error toast：aria-live="polite"（success）/ aria-live="assertive"（error）；不搶焦點；Wizard loading 中 ESC 不關閉（modal.dismissal.savingLocked）；失敗保留 wizard：焦點回到第一個 invalid 欄位（若能定位），或維持在確認按鈕上
  • ARIA：Loading button：aria-busy="true"；Toast：role="status"（success）/ role="alert"（error）；Wizard 全鎖中：wizard 容器加 aria-busy="true"

Angular 做法

  • pessimisticWizard：wizardSubmitting 用 signal，綁 [isSubmitting]="wizardSubmitting()" 驅動按鈕 loading；按鈕本身是 <app-button [loading]="...">（自動阻擋重複 click）。
  • savingLockedSurface：用 ng-content 投影進 wizard 的「取消」按鈕也要 guard，handler 第一行寫 if (this.wizardSubmitting()) return;
  • toast 服務在 Angular 是 ToastService：逐欄存檔 toast 用 ToastService.show() 一欄一顆、依序堆疊；ToastService.update() 的用途是同一件事的「進行中→完成」原地轉場。
  • toast 的 duration 由 toast.service.ts 裡的模組函式 resolveDuration() 決定（不是 ToastService 的方法），show() 與 update() 共用。
  • 逐欄存檔 toast 的封裝（例如使用端的 SaveToastService）由使用端實作，不在 DS 套件內。
